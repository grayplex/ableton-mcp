# Quick Task 260402-o86: Fix Duplicate Framing Protocol — Extract and Enforce Sync Summary

**One-liner:** Extracted Remote Script framing into `framing.py` canonical module and added `TestProtocolSync` to guard protocol constants against drift.

## What Was Done

The framing protocol (`_recv_exact`, `send_message`, `recv_message`) was previously defined inline in two places:
- `AbletonMCP_Remote_Script/__init__.py` (Remote Script runtime)
- `MCP_Server/protocol.py` (server-side)

Any framing change (e.g., adjusting the 10MB message limit or header format) required editing both files, with no automated check that they stayed in sync.

### Task 1: Extract Remote Script framing into framing.py

- Created `AbletonMCP_Remote_Script/framing.py` as the canonical framing source for the RS runtime
- Removed the inline function definitions from `__init__.py` (lines 35-68, including the `# --- Length-prefix framing protocol ---` comment block)
- Added `from .framing import _recv_exact, send_message, recv_message` to `__init__.py`
- Removed now-unused `json` and `struct` imports from `__init__.py`
- Added cross-reference comment to `MCP_Server/protocol.py` docstring pointing to RS canonical source

### Task 2: Add TestProtocolSync to test_protocol.py

Added `TestProtocolSync` class with 4 tests:
- `test_max_message_size_constant` — regex-extracts the MB multiplier from both files, asserts they match
- `test_header_format_constant` — asserts both files use `">I"` struct format and 4-byte header reads
- `test_rs_framing_module_exists` — structural check that `framing.py` exists on disk
- `test_rs_init_imports_from_framing` — asserts `__init__.py` imports from `.framing` and has no inline definitions
